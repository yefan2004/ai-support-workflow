## 1. 项目总目标

当前仓库中的邮件系统是一个 **Portfolio Demo**，用于展示一条可解释、可审核、带人工在环的 AI 辅助事件处理链路。它不是最终 SaaS，也不是生产级邮件平台，不能直接用于真实客户邮件或安全关键场景。

这个 Demo 真正要证明的核心能力不是“自动回邮件”，而是下面这条可复用链路：

```text
接收事件
  → 标准化
  → 去重
  → 规则判断
  → AI 辅助
  → 风险分流
  → 人工审核 / 接管
  → 后续动作
```

各环节的职责边界：

- **接收事件**：当前由 n8n 从 163 测试邮箱读取邮件，再调用 FastAPI；n8n 只负责触发、读取和编排。
- **标准化**：把输入整理为 FastAPI 需要的字段，当前是 `mailbox_id`、`message_id`、`subject`、`body`。
- **去重**：以 `mailbox_id + message_id` 作为当前邮件场景的幂等键，由 PostgreSQL 唯一约束兜底。
- **规则判断**：用明确的高风险关键词规则做前置拦截；规则命中时直接转人工，不调用 AI。
- **AI 辅助**：默认使用离线、确定性的 Mock Provider；显式配置后可切换 DeepSeek，用 AI 生成分类、摘要、风险说明和草稿。
- **风险分流**：普通且有可用草稿的任务进入 `awaiting_review`；高风险、退款/投诉、空正文或没有可用草稿的任务进入 `human_takeover`。
- **人工审核 / 接管**：人工执行 `approve`、`reject` 或 `takeover`，草稿可以编辑后随审核动作保存。
- **后续动作**：当前到“审核通过”为止；**没有真实发送，也没有 `sent` 状态**。

当前邮件只是第一个输入适配器。长期目标是把上述模式复用到业务事件、设备告警和机器人运营流程，但复用顺序必须是“先有第二个真实场景，再提取稳定抽象”，而不是现在就把整个邮件项目重构成通用事件框架。

产品原则应当保持清晰：

- AI 负责辅助分类、摘要和草稿，不负责最终决定。
- 规则负责高风险前置拦截，但关键词规则可能误判或漏判。
- 人负责最终审核、接管和对外动作授权。
- 系统不做未经人工批准的外部动作；`approved` 只表示审核通过，不表示已发送。
- 当前所有验证都是合成数据或有限测试，不构成生产稳定性证明。

## 3. 当前项目停止线

当前邮件 Demo 暂时不再增加以下业务功能：

- 自动邮件发送；
- Stripe；
- 多租户；
- AWS 生产部署；
- Supabase Auth；
- Slack；
- 完整分页；
- 生产级鉴权；
- 实时机器人控制；
- ROS 2 与邮件系统的强耦合；
- 通用事件框架的大规模重构。

这条停止线的含义是：**不再主动把邮件 Demo 做“更完整”**。邮件项目保持当前清晰、可演示、可审核的范围；后续只做必要的缺陷修复、安全修复和文档修正。第 4 节定义的 Docker 可复现工作已完成现有报告中的验证，不再作为继续扩张邮件功能的理由。

停止线的原因：

1. **这些功能应该由客户需求驱动。** 没有真实客户和明确验收标准时，提前做发送、计费、多租户或生产部署，很容易做成“看起来完整但没人需要”的功能。
2. **每一项都会显著扩大范围和风险。** 发送涉及送达率、退信、合规和误发；多租户涉及隔离、权限和计费；生产部署涉及安全、监控、备份和 SLA；实时控制涉及人身安全和实时性。这不是在现有 Demo 上“加一个按钮”的工作量。
3. **当前 Demo 已足以作为作品集和 Upwork 能力证明。** 它已经展示了输入接入、去重、规则、AI Provider 抽象、人工审核状态机和有限真实联调；继续打磨邮件 UI 的边际价值远低于开始获取客户反馈。
4. **当前验证不足以支撑生产承诺。** 规则是精确关键词，AI 只做了有限合成数据联调，n8n 只验证了测试邮箱，测试也没有在本次任务中重新运行。把 Demo 说成生产系统会带来不必要的信任风险。
5. **停止不是永远不做。** 如果客户明确付费、范围清楚、验收标准可写，相关功能应作为 Phase 5 的客户定制项目单独评估和报价，而不是在邮件 Demo 里继续无边界扩张。

## 4. Docker 本地可复现 Demo（已完成现有报告验证）

### 4.1 目标

让招聘方、潜在客户或未来合作者在新的机器上，用少量明确步骤启动同一条演示链路：

```text
PostgreSQL
  → Alembic 迁移
  → FastAPI（默认 Mock Provider）
  → Streamlit Review Dashboard
  → 合成邮件任务

```

这个阶段的目标是**可复现的演示环境**，不是生产部署。它必须默认离线、默认安全、默认不依赖真实邮箱和真实客户数据。

## 5. Upwork 接单计划

### 5.1 定位

当前阶段销售的不是“完整 SaaS”，而是**小而明确、能在有限时间内交付的自动化与集成能力**：

- 把客户已有的表单、邮件、Webhook、API、数据库或内部工具串起来；
- 对输入做清洗、校验、去重和分类；
- 用规则和 AI 辅助判断，但把最终决定保留给人；
- 提供一个简单可用的审核界面或操作入口；
- 用状态、审核记录和客户项目所需的最小日志让流程可追踪。

这一定位与当前邮件 Demo 展示的能力一致，也避免把项目承诺扩大到生产平台、实时控制或安全关键系统。

### 5.2 当前适合销售的服务

| 服务 | 可以承诺的最小交付 | 当前证据与边界 |
| --- | --- | --- |
| n8n workflow automation | 触发、读取/接收数据、字段映射、调用 HTTP API、基本错误分支、运行说明 | 仓库有 n8n 集成文档和早期 Webhook 工作流草稿；真实 IMAP 工作流在 n8n UI 中，仓库没有经过验证的导出文件。具体节点兼容性需按客户 n8n 版本做 Discovery。 |
| FastAPI / API integration | 小型 REST API、请求校验、数据库写入、迁移、健康检查、基础测试 | 仓库已有 FastAPI + PostgreSQL + Alembic + pytest 结构；可以直接作为起点。 |
| AI-assisted classification | 分类、摘要、风险说明、草稿生成；Provider 可替换；输出 schema 校验 | 已有 `AIProvider` 抽象、Mock 默认 Provider、可选 DeepSeek Provider 和 JSON 校验；真实 AI 只做了有限合成数据联调。 |
| human review workflow | 待审核列表、详情、可编辑草稿、approve / reject / takeover、状态记录 | 已有 `/ui`、Streamlit 收件箱和审核 API；当前 `reviewed_by` 是自报演示值，没有生产级身份鉴权。 |
| email or event triage | 输入登记、去重、规则前置拦截、AI 辅助分流、人工审核 | 邮件链路已有有限真实验证；事件场景需要重新定义字段和规则，不能直接宣称已支持所有事件源。 |
| webhook automation | Webhook 接收、字段校验、幂等键、任务创建、状态查询 | 早期 n8n 草稿展示了 Webhook → 登记 → process/GET 的编排思路；真实错误分支和容器网络尚未验证。 |
| internal operations workflow | 把内部请求转成任务，按规则分流，人工处理并留下状态 | 可以复用当前“任务 + 状态机 + 审核”的模式；需要按客户流程重新设计字段和权限。 |

销售时的准确说法是“我可以用这套模式做一个小的、可演示的自动化”，而不是“我有一个成熟平台，可以覆盖你的全部业务”。

### 5.3 当前不应直接承诺

以下内容不应在简历、作品集、Proposal 或客户沟通中直接承诺：

- **production-ready SaaS**：当前没有生产级鉴权、租户隔离、SLA、备份、监控和合规能力。
- **complete email sending platform**：当前没有真实邮件发送、送达率、退信处理或发送合规能力。
- **AWS production architecture**：仓库没有 AWS 部署实现或生产运行记录；可以讨论迁移方案，但不能说已经交付过。
- **real-time robot control**：当前没有 ROS 2、实时控制、急停或安全认证能力。
- **multi-tenant platform**：当前没有租户模型、数据隔离、计费或租户级权限。
- **zero-risk or never-fail system**：AI 会误判，规则会漏判，网络和数据库会失败；不能承诺零风险或永不失败。

如果客户需要这些内容，正确动作是：

1. 说明当前能力边界；
2. 建议先做 paid discovery；
3. 把范围拆成可验证的小阶段；
4. 对安全关键或实时控制部分明确说“不接”或引入合格合作方；
5. 不把“以后可以做”写成“现在已具备”。

### 5.4 投递流程

1. **发布作品集。**
   - 使用当前 GitHub 仓库、README、架构图和合成数据截图；

   - 所有素材只使用合成邮件和脱敏数据。

2. **优先投具体的 n8n / API / AI workflow 小型项目。**
   - 优先选择输入、输出、平台和验收标准相对清楚的项目；
   - 优先选择“把两个系统接起来”“把人工流程自动化一部分”“做一个内部审核工具”这类范围；
   - 不优先投“从零搭建完整 SaaS”“实时机器人控制”“安全关键系统”。

3. **先确认输入、输出、平台、预算和验收标准。**
   - 输入从哪里来：邮件、表单、Webhook、数据库、文件还是消息平台？

   - 失败时怎么处理：重试、告警、人工接管还是停止？

4. **对范围不清楚的项目提议 paid discovery。**
   - Discovery 的交付物是需求澄清、流程草图、数据字段、风险清单、实施阶段和报价，不是免费完整方案；

   - 不把“先做出来看看”当成免费试做。

5. **不为低预算项目承诺完整 SaaS。**
   - 低预算项目只承诺一个明确的小交付，例如一个 Webhook、一条 n8n 流程、一个审核页面或一次 API 集成；
   - 发送、鉴权、多租户、部署和长期运维单独计价；
   - 如果预算不足以覆盖范围，礼貌拒绝或缩小范围。

6. **记录投递、回复和客户需求，按市场反馈调整方向。**
   - 记录项目来源、客户行业、需求、预算、回复、拒绝原因和成交情况；
   - 区分“客户不感兴趣”和“客户需要但我暂时不能交付”；
   - 如果多个客户都问设备告警或 ROS 2 事件接入，再进入 Phase 3/4；
   - 如果客户主要问邮件发送或 AWS 部署，先判断是否值得做 Phase 5 的定制，而不是立刻改邮件 Demo。

## 7. 第二个 Demo：设备/机器人告警

本节只规划范围和验收标准，**不实现代码**。目标是用最小成本验证：当前“事件接收 → 去重 → 规则 → 任务 → 人工审核”的核心模式，能否自然迁移到设备告警场景。

### 7.1 目标

做一个最小的 Robot/Device Alert Demo：

- 接收设备或机器人系统发出的告警事件；
- 校验字段并标准化；
- 按 `device_id + event_id` 去重；
- 用规则判断是否需要人工关注；
- 创建可查询、可审核的任务；
- 允许 operator review 或 takeover；
- 记录状态和处理结果，便于审计。

这个 Demo 证明的是**告警事件接入和人工处置流程**，不是机器人控制平台。同一模式也可以承接机器人任务事件（任务创建、分配、执行中、失败、完成）的记录与人工确认，但当前只取“设备告警”这个最小切口，不把任务管理、调度或控制混进第一个迁移场景。

### 7.2 示例输入

```json
{
  "device_id": "robot-07",
  "event_id": "battery-2025-001",
  "event_type": "low_battery",
  "severity": "medium",
  "message": "Battery level dropped below the configured threshold."
}
```

字段含义（规划）：

| 字段 | 含义 | 约束 |
| --- | --- | --- |
| `device_id` | 设备或机器人标识 | 必填、非空、最大长度需定义 |
| `event_id` | 事件唯一标识，由来源系统生成 | 必填、非空；与 `device_id` 组成幂等键 |
| `event_type` | 事件类型，例如 `low_battery` | 必填；需要允许列表或明确未知类型处理 |
| `severity` | 严重程度，例如 `low` / `medium` / `high` / `critical` | 必填；枚举值需固定 |
| `message` | 人类可读描述 | 可选或必填由实现阶段决定；应限制长度 |

### 7.3 目标流程

```text
Webhook
→ 字段校验
→ device_id + event_id 去重
→ 规则判断
→ 创建任务
→ operator review / takeover
→ 状态记录
```

建议的最小行为：

1. `POST /api/v1/device-events` 接收事件；字段无效返回 `422`。
2. 首次事件创建任务，状态为 `received`；重复 `device_id + event_id` 返回已有任务和 `duplicate=true`，不新增记录。
3. 处理时先执行规则；规则命中高风险时直接进入 `human_takeover` 或待处理队列，不调用 AI。
4. 规则未命中时可以调用 AI 做摘要或分类；AI 输出必须经过 schema 校验，且 `requires_human` 始终为 true。
5. 需要人工关注的事件进入 `awaiting_review`；operator 可以 `acknowledge`、`reject` 或 `takeover`。
6. 每个动作都记录操作者、时间、备注和状态变化；但当前 `reviewed_by` / `operator_id` 仍只能是演示值，除非客户项目另行实现真实鉴权。
7. 任何状态都**不会**自动转换为设备控制命令。

建议的最小状态（仅规划，不是已实现）：

```text
received → processing → awaiting_review → acknowledged / rejected / human_takeover
                     ↘ human_takeover / failed
```

状态语义要在实现时写清楚：

- `acknowledged` 只表示“操作员已确认收到/已知悉”，不表示设备已修复，也不表示机器人已执行动作。
- `human_takeover` 表示需要人工接管处置，不表示已经联系现场或完成维修。
- `failed` 表示告警处理失败，不表示设备故障已被处理。

### 7.4 最小规则示例（规划）

| 条件 | 建议动作 |
| --- | --- |
| `severity=critical` | 进入 `human_takeover`，优先人工处理 |
| `event_type=low_battery` 且 `severity=medium` | 创建任务，进入 `awaiting_review` |
| 未知 `device_id` | 进入 `human_takeover`，要求人工确认设备身份 |
| 未知 `event_type` | 进入 `human_takeover`，不猜测含义 |
| 重复 `device_id + event_id` | 返回已有任务，不重复创建 |
| 字段缺失或非法 | `422`，不创建任务 |
| AI 调用失败或输出无效 | 标记 `failed` 或转人工；不能静默丢弃告警 |

这些规则只是 Demo 范围，不是通用告警策略；真实客户项目必须重新确认严重程度定义、升级路径和值班流程。

### 7.5 验收标准

## 8. ROS 2 复用方向

### 8.1 推荐架构

```text
ROS 2 Node
→ Topic / Service
→ Bridge Node
→ FastAPI Event API
→ Rules / Task / Human Review
```

推荐的职责划分：

| 层 | 负责 | 不负责 |
| --- | --- | --- |
| ROS 2 Node / 控制器 | 实时控制、传感器读取、导航、避障、安全动作、急停 | 业务审核、工单流转、客户界面 |
| Bridge Node | 只读订阅需要上报的 Topic/Service；把 ROS 2 消息标准化为事件；生成稳定事件 ID；调用 FastAPI | 向机器人发布控制命令；替代安全控制器；做业务决策 |
| FastAPI Event API | 字段校验、去重、规则、任务创建、状态机、人工审核、审计 | 实时控制、电机指令、导航、避障、急停 |
| Rules / AI | 规则前置拦截；AI 辅助分类、摘要、风险说明、草稿或建议 | 直接决定安全关键动作；替代人工审批 |
| Human Review | operator 查看、确认、拒绝、接管、备注 | 绕过安全控制器；直接驱动执行机构 |

### 8.2 适合接入的事件

- 电量告警；
- 定位失败；
- 传感器异常；
- 任务失败；
- 机器人任务状态（创建、分配、执行中、完成、失败）；
- 禁区事件；
- 巡检结果；
- 需要人工确认的设备状态；
- 其他“需要记录、分流、通知或人工处置”的非实时事件。

这些事件的共同点是：**需要业务层记录和人工判断，而不是毫秒级控制回路**。

### 8.3 明确边界

- **ROS 2 / 控制器负责实时控制和安全动作。** 包括电机控制、导航、避障、急停、安全联锁等。
- **FastAPI 负责事件、任务、告警、人工接管和审计。** 它可以记录“发生了什么”和“谁处理了”，但不控制“机器人下一步怎么动”。
- **AI 不直接决定安全关键动作。** AI 可以摘要、分类、建议，但输出必须经过规则、schema 校验和人工审核。
- **Bridge 默认只读。** 不订阅或发布控制类 Topic；不把 FastAPI 的审核结果自动转换成 `cmd_vel`、导航目标、机械臂指令或急停信号。
- **审核通过不等于设备已恢复。** `acknowledged` 或 `approved` 只表示人工确认，不表示故障已修复或动作已完成。
- **网络中断和消息重复必须显式处理。** 事件 ID、时间戳、QoS、重试/缓冲策略由客户环境和 ROS 2 版本决定，当前尚未验证。

### 8.4 最小 Bridge 设计原则（规划）

- 只订阅明确允许上报的 Topic/Service；
- 把 ROS 2 消息映射为稳定的事件 schema，不把原始消息直接透传给业务层；
- 事件 ID 尽量来自来源系统；没有稳定 ID 时，使用设备 ID + 时间戳 + 序列号等组合并明确碰撞风险；
- 保留来源时间、接收时间和设备标识；
- 调用 FastAPI 时设置超时，不无限阻塞 ROS 2 回调；
- 失败时记录日志并进入人工/离线处理，不把失败伪装成成功；
- 不做控制指令回写；
- 不在 Bridge 中存放生产 API Key 或明文凭据。

### 8.5 当前未实现与未验证

- 仓库没有 ROS 2 代码、Bridge Node、消息定义或仿真环境；
- 没有验证 ROS 2 发行版、DDS、QoS、网络拓扑、时间同步和安全策略；
- 没有验证 Bridge 到 FastAPI 的延迟、吞吐和断线恢复；
- 没有验证任何真实机器人或安全控制器；
- 没有实时控制、急停或安全认证能力。

因此，ROS 2 方向只能作为 Phase 4 的独立 Demo 规划，不能从当前邮件项目直接承诺为客户交付实时机器人系统。

### 9.1 决策规则

- 客户需求只涉及“接收事件、整理字段、去重、规则、AI 辅助、人工审核”时，优先考虑复用当前核心。
- 客户需求涉及**真实发送、真实客户数据、生产鉴权、多租户、SLA**时，必须先做 Discovery，并把新增能力单独报价。
- 客户需求涉及**实时控制、急停、导航、避障、安全关键动作**时，当前不接；不要用“AI + FastAPI”包装成实时控制系统。
- 客户无法说清输入、输出、平台、预算或验收标准时，不报固定总价；提议 paid discovery。
- 客户预算只够一个小脚本，却要求完整 SaaS 时，缩小范围或拒绝，不做免费兜底。
- 客户要求“AI 自动决定并执行”时，明确说明当前产品原则是 human-in-the-loop，AI 不直接执行外部动作。

### 9.2 需要警惕的红旗信号

- “先做出来，需求以后再说”；
- “没有验收标准，先上线看看”；
- “预算很低，但要完整平台、发送、鉴权和部署”；
- “需要 AI 直接控制机器人/设备”；
- “需要实时控制，但不能提供安全负责人或测试环境”；
- “直接把真实客户邮件/生产数据发给外部模型”；
- “必须保证零误判、零漏判、永不失败”。

遇到这些信号时，正确动作是先澄清或拒绝，而不是先承诺。

- 每个投递项目都确认了输入、输出、平台、预算和验收标准，或明确进入 paid discovery；
- 所有客户沟通都准确描述 Demo 边界；
- 投递和回复有记录，能看出哪类需求有市场；
- 达到自己设定的周投递目标（建议从少量精准投递开始，再按反馈调整，不追求盲目数量）；
- 没有因为投递而重新打开邮件 Demo 的无边界开发。

**进入下一阶段的条件**

- 出现第一个 paid discovery 或小型付费项目；或
- 多个潜在客户持续询问设备告警/机器人事件方向，足以证明值得做第二个 Demo；或
- 投递一段时间后仍无有效回复，需要调整定位、文案或目标项目类型，而不是继续加邮件功能。

### Phase 3：设备/机器人告警 Demo

**状态：有客户反馈或 Docker 完成后再做**

**目标**

用最小实现验证同一套“事件接收 → 去重 → 规则 → 任务 → 人工审核”的核心可以迁移到设备/机器人告警场景，并形成一个可用于 Upwork 展示的第二个 Demo。

**交付物**

- 一个最小 `POST /api/v1/device-events` Webhook（路径名可在实现时调整）；
- 事件字段 schema 和校验；
- 设备告警任务表，包含 `device_id + event_id` 唯一约束；
- 规则服务和最小风险分级；
- 任务状态机：接收、处理中、待审核、已确认/拒绝/人工接管、失败；
- operator review / takeover 接口或最小界面；
- 合成 `low_battery` 等事件样例；
- 最小测试：创建、去重、规则、审核、失败路径；
- README：能力、限制、安全边界；
- 截图或短视频。

**不包含**

- 电机控制；
- 导航；
- 避障；
- 紧急制动；
- 安全关键动作；
- AI 直接控制机器人；
- 真实设备或生产机器人接入；
- 实时控制回路；
- 自动派单、现场维修调度和 SLA；
- 生产级鉴权、审计合规、多租户；
- ROS 2 Bridge（留到 Phase 4）。

**验收标准**

- 第 7.5 节验收清单全部通过；
- 合成事件可以创建任务并进入审核/接管；
- 重复事件不会新增任务；
- 规则命中时不会调用 AI 或执行外部动作；
- operator 可以查看、确认、拒绝或接管；
- 状态和操作记录可查询；
- 不向任何设备、机器人或 ROS 2 主题发送控制命令；
- 文档明确说明这是告警处置 Demo，不是机器人控制产品。

**进入下一阶段的条件**

- 设备告警 Demo 通过验收并稳定；
- 出现真实 ROS 2 事件接入需求或明确客户场景；
- 客户能够提供 ROS 2 版本、消息定义、测试环境和安全边界；
- 如果以上不成立，停留在 Phase 3，把 Demo 用于投递，不为了技术兴趣继续做 ROS 2。

### Phase 4：ROS 2 Bridge Demo

**状态：第二个 Demo 稳定后再做**

**目标**

做一个只读的 ROS 2 Bridge Demo，验证 ROS 2 事件可以被标准化并送入 FastAPI 的任务/人工审核流程，同时不触碰实时控制和安全动作。

**交付物**

- 一个最小 ROS 2 Bridge Node；
- 只读订阅白名单 Topic/Service；
- ROS 2 消息到事件 schema 的字段映射；
- 稳定事件 ID 和去重策略说明；
- 合成 publisher 或仿真环境；
- Bridge 到 FastAPI 的超时、错误日志和失败处理；
- 最小测试：消息映射、重复事件、API 不可用、无效消息；
- 架构图、运行说明和安全边界文档；
- 演示截图或短视频。

**不包含**

- 向 ROS 2 发布控制命令；
- 电机控制、导航、避障、急停、安全联锁；
- AI 直接控制机器人；
- 真实生产机器人接入；
- 生产级 ROS 2 部署、QoS 调优、实时性保证和 SLA；
- 安全认证；
- 把 FastAPI 审核结果自动转换为机器人动作。

**验收标准**

- 仿真 ROS 2 事件可以从 Bridge 进入 FastAPI，并创建任务；
- 重复事件不会新增任务；
- 无效消息被拒绝并记录，不会静默丢失；
- Bridge 只订阅白名单事件，不发布控制 Topic；
- FastAPI 不可用时，Bridge 不会伪装成功，也不会控制机器人；
- 文档明确说明这是只读事件接入 Demo；
- 代码和测试均不包含控制指令路径。

**进入下一阶段的条件**

- Bridge Demo 通过验收并稳定；
- 出现真实客户 ROS 2 集成需求；
- 客户提供 ROS 2 版本、消息定义、测试环境、网络和安全负责人；
- 安全边界已经书面确认：ROS 2/控制器负责实时控制，FastAPI 只做事件和人工审核；
- 如果这些条件不成立，停止在 Phase 4，不继续为了技术展示扩展实时控制。

### Phase 5：客户定制集成

**状态：按客户需求报价**

**目标**

在客户明确需求、预算和验收标准的前提下，用当前可复用核心交付一个定制集成项目，而不是继续扩大邮件 Demo。

**交付物**

- Discovery 记录：业务流程、输入、输出、平台、权限、数据、风险；
- SOW / 范围说明：包含、不包含、假设、依赖、里程碑、验收标准；
- 报价和付款节点；
- 定制实现：适配器、规则、任务状态、审核流程、必要的 API/UI；
- 测试：至少覆盖主流程、重复输入、失败路径和权限边界；
- 部署/运行文档和 handover；
- 安全与数据处理说明；
- 支持边界和变更流程。

**不包含**

- 没有边界的“先做做看”；
- production-ready SaaS 的泛化承诺；
- 实时控制、安全关键动作；
- 未经评估的多租户、计费、SLA；
- 7×24 支持；
- 无限修改和免费新增需求；
- 使用真实客户数据做公开演示。

**验收标准**

- 客户确认 SOW 和验收标准；
- 主流程在客户提供的测试环境或合成数据上通过；
- 重复输入、失败路径和权限边界有明确行为；
- 文档和 handover 完成；
- 密钥、凭据和客户数据没有进入仓库或公开作品集；
- 交付内容与 SOW 一致，没有把未实现能力写成已完成；
- 客户书面确认验收。

**进入下一阶段的条件**

- 客户明确提出实时控制或安全关键需求；
- 该需求有独立预算、合格的安全/实时工程资源、测试环境和合同；
- 通过 Phase 6 的独立评估；
- 否则不进入实时控制，只继续做事件、任务、审核和集成类项目。

### Phase 6：实时控制系统

**状态：单独评估，不从当前邮件项目直接承诺**

**目标**

只在具备安全工程、实时系统、合同和保险条件的前提下，评估是否进入实时机器人控制领域。这个阶段不是当前邮件项目的自然延伸，也不是 Upwork 小项目的升级版。

**交付物**

- 独立的安全风险评估；
- 实时架构设计：控制回路、时限、故障安全、降级、急停和监控；
- 硬件在环（HIL）或仿真验证计划；
- 独立安全评审和认证路径（如适用）；
- 责任、保险、合同和支持边界；
- 与合格 ROS 2/机器人团队的合作方案；
- 明确的“不做什么”清单。

**不包含**

- 把当前 FastAPI 当作实时控制器；
- 让 AI 直接生成或执行控制指令；
- 把审核通过自动转换为电机、导航、避障或急停动作；
- 没有安全评审就上真实机器人；
- 没有认证和合同就承诺安全关键系统；
- 用 Portfolio Demo 证明实时安全性。

**验收标准**

- 有独立的安全负责人和评审记录；
- 实时性、故障安全和降级行为有可验证指标；
- 有 HIL/仿真和现场测试计划；
- 有明确的责任、保险和合同边界；
- 通过适用的法规/认证评估；
- 没有把当前 Demo 的测试结果当作安全证明。

**进入下一阶段的条件**

- 不自动进入。必须是新的客户、独立预算、合格团队/合作方和完整安全评估；
- 如果这些条件不满足，明确不接；
- 当前邮件项目和第二个 Demo 都不应成为实时控制承诺的依据。

## 12. 最终原则

- 不为了看起来完整而盲目加功能。
- 不把 Demo 说成生产系统。
- 不把 `approved` 说成 `sent`。
- 不把有限测试说成稳定性证明。
- 不让 AI 直接控制安全关键动作。
- 先交付可复现 Demo，再根据客户需求扩展。
- 优先复用稳定的基础设施和模式，而不是复制全部业务代码。
- 客户来了以后，优先解决明确问题，再决定技术方案。

文档维护规则：当 Docker 验收完成、第一个客户项目开始，或设备/ROS 2 范围发生变化时，更新本路线图和 README 的事实口径；不要只更新宣传文案而不更新限制。

> “当前最重要的下一步：基于已完成现有报告验证的 Docker 本地 Demo，开始 Upwork 投递；不要在邮件 Demo 上继续无限打磨。”
